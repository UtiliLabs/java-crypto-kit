help tomcat - Tomcat JNDI DataSource에서 암호화한 DB 접속정보 사용(DBCP2 또는 Tomcat JDBC Pool)

동작
  Resource에 factory="io.javacryptokit.jdbc.tomcat.EncryptedDataSourceFactory"를 지정하면, Tomcat이 DataSource를 만들 때
  password(암호화했다면 username도)를 복호화해 Tomcat 공식 Pool(DBCP2 또는 Tomcat JDBC Pool)에 넘깁니다.
  웹 애플리케이션 코드는 바꾸지 않습니다. 평문 password는 거부합니다.

지원 Tomcat 버전(모두 같은 JAR 하나, 괄호는 그 Tomcat이 요구하는 최소 Java)
  11.0(Java 17+) / 10.1(Java 11+) / 9.0(Java 8+)
                     지원. DBCP2·Tomcat JDBC Pool 모두 Docker 실서버에서 JNDI 조회 -> 연결 -> SQL 실행을 확인했습니다.
  8.5(Java 8+)       레거시(Apache 지원 종료: 2024-03-31). 같은 방식으로 동작을 확인했지만 신규 도입은 권장하지 않습니다.
  구형 Oracle JDK 8(8u161 미만)은 AES-256에 무제한 암호 정책이 필요합니다. 8u151~8u160은 java.security의
  crypto.policy=unlimited, 그 이전은 JCE Unlimited Strength 정책 파일. 없으면 [사유: CRYPTO_PROVIDER]로 실패합니다.
  DB 연결은 Tomcat Pool과 JDBC 드라이버가 합니다. 실증한 DB는 MariaDB이며, 다른 DB도 해당 JDBC 드라이버로 같은 방식으로
  설정할 수 있지만 실증하지 않았습니다.

한 Tomcat JVM의 공통 범위
  키 공급원·키ID·Pool 종류(crypto.pool.factory)는 JVM 전체에 하나입니다. Resource마다 다른 키나 Pool이 필요하면
  Tomcat 인스턴스(CATALINA_BASE)를 나눕니다. 여러 서버에는 같은 키 내장 JAR를 배포하고 fingerprint로 같은 키인지 확인합니다.

1) 설치(재빌드 없음)
  {jar}(또는 config embed-key로 만든 키 내장 JAR)와 JDBC 드라이버 JAR를 CATALINA_BASE/lib에 복사합니다.
  lib에는 java-crypto-kit JAR를 하나만 둡니다. Pool 라이브러리도 같은 lib에 있어야 합니다(tomcat-dbcp.jar는 Tomcat에
  포함, Tomcat JDBC Pool은 없으면 Tomcat 버전에 맞는 tomcat-jdbc.jar 추가).
  Windows: Copy-Item .\{jar} C:/tomcat/lib/
  Linux  : cp ./{jar} /opt/tomcat/lib/ && chown tomcat:tomcat /opt/tomcat/lib/{jar}

2) DB 비밀번호 암호화(Tomcat과 같은 JAR·설정으로)
  java -jar {jar} encrypt          -> ENC[v1:prod01:...]

3) Resource 작성
  넣을 곳(Tomcat이 실제로 읽는 파일)
    웹 애플리케이션의 META-INF/context.xml 또는 CATALINA_BASE/conf/Catalina/localhost/<앱>.xml   앱별 Resource(일반적)
    CATALINA_BASE/conf/context.xml   모든 웹 애플리케이션의 기본 Context(앱마다 Pool이 따로 생기므로 주의)
    conf/server.xml의 GlobalNamingResources + 각 앱의 ResourceLink   여러 앱이 Resource 하나를 함께 쓸 때
  이미 있는 파일이면 <Context> 안에 <Resource ... /> 한 개만 붙여 넣습니다(파일 전체를 바꾸지 않음).
  저장소의 docs/tomcat/dbcp2-context.xml·jdbc-pool-context.xml은 같은 내용의 예제이며 Tomcat이 직접 읽지 않습니다.

  3a) DBCP2(기본값: 아무 설정도 하지 않으면 DBCP2)
  <Resource name="jdbc/appDS" auth="Container" type="javax.sql.DataSource"
            factory="io.javacryptokit.jdbc.tomcat.EncryptedDataSourceFactory"
            driverClassName="org.mariadb.jdbc.Driver" url="jdbc:mariadb://db.example.internal:3306/app"
            username="app" password="ENC[v1:prod01:...]"
            initialSize="1" maxTotal="20" maxIdle="10" maxWaitMillis="10000"
            validationQuery="SELECT 1" testOnBorrow="true"/>

  3b) Tomcat JDBC Pool(crypto.pool.factory=org.apache.tomcat.jdbc.pool.DataSourceFactory를 지정했을 때)
  <Resource name="jdbc/appDS" auth="Container" type="javax.sql.DataSource"
            factory="io.javacryptokit.jdbc.tomcat.EncryptedDataSourceFactory"
            driverClassName="org.mariadb.jdbc.Driver" url="jdbc:mariadb://db.example.internal:3306/app"
            username="app" password="ENC[v1:prod01:...]"
            initialSize="1" maxActive="20" maxIdle="10" maxWait="10000"
            validationQuery="SELECT 1" testOnBorrow="true"/>

  Pool 선택은 Resource 속성이 아니라 설정 crypto.pool.factory로 하며 JVM의 모든 Resource에 적용됩니다.
    JAR에 저장: java -jar {jar} config set crypto.pool.factory=org.apache.tomcat.jdbc.pool.DataSourceFactory --operator <ID>
    또는 외부 Properties, 또는 CATALINA_OPTS의 -Dcrypto.pool.factory=...

  속성 설명
    name                 앱이 java:comp/env/jdbc/appDS 로 찾는 JNDI 이름
    auth                 Tomcat 표준 속성(Container 또는 Application). 일반 DB Resource는 Container.
                         Application은 앱이 리소스 관리자에 직접 인증하는 설계용이며, 이것만 바꿔 DB 계정이 바뀌지 않습니다.
    type                 javax.sql.DataSource만 지원합니다(Tomcat 10.1·11에서도 javax.sql).
    factory              두 Pool 모두 같은 암호문 복호화 Factory를 씁니다.
    password / username  password는 ENC[...] 또는 B64[...] 필수, username은 평문 또는 암호문
    scope / singleton    표준 선택 속성(기본 Shareable / true). 일반 DataSource는 기본값을 유지합니다.
    그 밖의 Pool 속성     공식 Pool에 그대로 넘깁니다. 이름은 Pool마다 다릅니다(DBCP2: maxTotal·maxWaitMillis /
                         Tomcat JDBC: maxActive·maxWait). 실제 지원 여부는 Tomcat·Pool 버전을 따릅니다.
  Tomcat 밖(WebLogic·JEUS·Spring Boot 기본 DataSource)에는 이 Resource 설정을 그대로 쓰지 않습니다.

4) Tomcat용 외부 설정(JAR 내장 설정을 쓰지 않을 때만)
  Linux          bin/setenv.sh  : CATALINA_OPTS="$CATALINA_OPTS -Dcrypto.config.file=/etc/java-crypto-kit/app.properties"
  Windows 콘솔   bin/setenv.bat : set "CATALINA_OPTS=%CATALINA_OPTS% -Dcrypto.config.file=C:/secure/app.properties"
                 (startup.bat·catalina.bat으로 실행할 때만 읽습니다)
  Windows 서비스 서비스는 setenv.bat을 읽지 않습니다. Tomcat 서비스 설정 도구(예: tomcat9w.exe의 Java 탭 Java Options)에
                 -Dcrypto.config.file=C:/secure/app.properties를 한 줄로 추가하거나, 명령으로
                 tomcat9.exe //US//Tomcat9 ++JvmOptions=-Dcrypto.config.file=C:/secure/app.properties
                 처럼 바꾼 뒤 서비스를 재시작합니다(실행 파일·서비스 이름은 설치한 Tomcat에 맞게). 실서버 미검증입니다.
  키 환경변수는 Tomcat 서비스 계정에 전달되어야 합니다(systemd Environment=, Windows 서비스의 환경 설정).

5) 재시작과 확인
  Tomcat을 멈추고 다시 시작한 뒤 애플리케이션에서 DB 연결을 확인합니다(JNDI 조회와 쿼리 1건).
  initialSize > 0이면 기동할 때 첫 연결을 만들므로 DB 비밀번호가 틀리면 Tomcat 로그에 바로 나타납니다.
  설정·키는 DataSource를 만들 때 읽으므로 바꾼 뒤에는 Tomcat을 재시작합니다.

키 교체 순서
  rekey -> password 교체 -> 서버별 JAR 배포와 fingerprint 확인 -> 재시작 -> 실제 SQL 확인
  (끝날 때까지 이전 JAR·이전 암호문을 원복용으로 보관). Vault는 crypto.vault.ver로 버전을 고정합니다.

대표 오류와 해결(Tomcat 로그의 [java-crypto-kit]로 시작하는 줄)
  [사유: PLAINTEXT_PASSWORD]   -> password가 ENC[...]/B64[...]가 아닙니다. 2)로 암호화하세요.
  [사유: KEY_ID_MISMATCH]      -> 다른 키ID로 만든 암호문입니다. 그 암호문을 만든 JAR·설정을 쓰세요.
  [사유: INTEGRITY]            -> 다른 키입니다. 양쪽에서 java -jar {jar} fingerprint로 비교하세요.
  [사유: KEY_SOURCE]           -> 키 파일·환경변수·Vault·KMS를 읽지 못함. Tomcat 실행 계정으로 doctor를 실행하세요.
  [사유: CONFIGURATION]        -> 설정 이름·값 오류(예: -D 오타, 외부 Properties의 없는 항목). doctor로 확인하세요.
  [사유: POOL_FAILURE] (원인 유형: ...SQLState=28000) -> DB가 로그인을 거부했습니다. DB 비밀번호 자체를 확인하세요.
  [사유: POOL_FAILURE] (원인 유형: ClassNotFoundException) -> CATALINA_BASE/lib에 Pool 또는 JDBC 드라이버 JAR가 없습니다.
  이 라이브러리는 비밀번호를 로그에 남기지 않습니다. 기동 후(getConnection) Tomcat·JDBC 드라이버가 직접 출력하는
  메시지는 이 라이브러리 범위 밖입니다.

관련 명령: encrypt, doctor, fingerprint, config embed-key, config help
